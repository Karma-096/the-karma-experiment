# Приватная аналитика THE KARMA EXPERIMENT

Дата проверки: 1 ноября 2026 года. Реализация предназначена для отдельного PR; развёртывание и включение требуют утверждения владельца.

## Что проверено до реализации

- Исходная ветка `main`: `2761ce2` (объединение PR №4). HTML действующего GitHub Pages на момент проверки побайтово совпал с `main/index.html`: SHA-256 `e4424ee5f9af2a85aa3e89891ec53743c2aaa04d208ef65812ed935b4f12327c`.
- Поиск по репозиторию не выявил Google Analytics, Plausible, Umami, GoatCounter, Cloudflare Web Analytics или собственного учёта посещений.
- В доступной базе Supabase не найдено прикладных таблиц аналитики/посещений/событий. `storage.buckets_analytics` относится к инфраструктуре Storage и не является аналитикой сайта. В списке развёрнутых Edge Functions есть только `submit-karma-message` и `scan-crypto-contributions`.
- Проверены агрегаты журналов Supabase за доступные последние 24 часа. 672 записи `edge_logs` относятся к трём RPC криптосканера: 480 checkpoint, 96 finish, 96 claim. Это запросы инфраструктуры, а не 672 посещения сайта. Отсутствие других записей в этом окне не доказывает отсутствия посетителей.
- Проверены имена полей журналов, без чтения значений IP или индивидуальных запросов: присутствуют сетевые IP-поля, User-Agent и другие сетевые метаданные. Поэтому браузерная аналитика через новый публичный Supabase endpoint добавляла бы записи в такие журналы.
- GitHub Traffic измеряет посещения **репозитория**, а не воронку GitHub Pages. Коннектор не предоставляет разрешённый endpoint Traffic/Pages access logs; статистика репозитория не использована как статистика сайта.
- Turnstile Analytics может показывать результаты проверок и проверки токенов. Но виджет загружается при открытии страницы, может обновляться при смене языка и не измеряет заполнение/приём формы. Доступа к панели Cloudflare/возможной отдельной внешней аналитике в этой сессии нет. Её отсутствие во всех сторонних аккаунтах не утверждается.

Вывод: доступные измерения полезны для диагностики инфраструктуры, но не заменяют общий знаменатель посещений и обезличенные этапы формы. Новая система не дублирует найденную аналитику сайта: такой аналитики не обнаружено в доступных источниках.

## Реализация

Браузер → Cloudflare Worker `/collect` → выделенная D1 через внутреннюю привязку `ANALYTICS_DB`.

В базе только две таблицы: системные настройки и `daily_counts(day, event, total)`. При поступлении события атомарно увеличивается суточный счётчик. Отдельной строки события, точного времени посещения и связи между событиями разных посетителей нет. Дата задаётся сервером в UTC; присланные даты и произвольные поля отвергаются.

Worker не делает HTTP-запросов в Supabase или к другому серверу, не использует ключи Supabase, не читает IP/Cookie/User-Agent/Referer/CF metadata и не пересылает исходный запрос. Это исключает перенос сетевых заголовков посетителя в журналы нового аналитического endpoint Supabase. Существующие процессы сообщений, модерации, Turnstile, криптосканера и платежей не изменяются.

Три независимых выключателя по умолчанию закрыты: `KARMA_ANALYTICS_ENABLED=false`, Worker `ANALYTICS_ENABLED="false"`, D1 `analytics_settings.enabled=0`. URL приёмника пуст, ID базы — явная нулевая заглушка. Сбор не начнётся от одного лишь слияния PR. В PR нет workflow автоматического развёртывания Worker/D1.

## Приватность

- Из браузера уходит только `{"event":"значение_из_списка"}`. Тексты сообщений, псевдонимы, страна, язык, адрес страницы, параметры URL, referrer, токены Turnstile, submission ID, IP и отпечатки устройства не входят в payload и не хранятся в аналитике.
- Аналитика не создаёт cookie, localStorage/sessionStorage, случайные ID, хеши IP или пользовательские сессии. Существующее хранилище языка/антиспам-паузы формы остаётся прежним.
- `credentials: omit`, `referrerPolicy: no-referrer`; DNT и Global Privacy Control отключают отправку.
- Каждый тип события учитывается один раз за срок жизни загруженной страницы. Переключение языка, возврат в вкладку и повторные клики не создают повторного события того же типа. Перезагрузка/новая вкладка — новое посещение; уникальные люди не вычисляются.
- В конфигурации Worker явно отключены Observability, invocation logs, traces и Logpush. В коде нет журналирования запросов, ошибок с данными пользователя или тела запроса. Нет Tail Workers и внешних log destinations.
- Нет публичного API чтения отчёта, выполнения SQL или управления настройками. Отчёт доступен только через авторизованную панель/CLI Cloudflare с правами на D1.
- До 90 календарных дней суточных агрегатов: сегодня и 89 предыдущих дней. Очистка выполняется при обработке событий; при полном отсутствии запросов старые агрегаты остаются до следующего запроса или ручной очистки. Это не жёсткое расписание удаления. Резервные копии D1 управляются политикой провайдера.

Хостинг неизбежно обрабатывает IP при сетевом соединении. Отключение журналов Worker и отсутствие IP в нашей базе не обещают отсутствия любых внутренних служебных данных у Cloudflare, GitHub или существующей защиты Turnstile. Перед запуском необходимо проверить фактические настройки аккаунта, отсутствие Tail/Logpush/сторонних журналов и соответствие уведомления о приватности. Настройки существующей антиспам-защиты не менялись.

## Доступные показатели после запуска

Все счётчики относятся к загрузкам страниц, где измерение разрешено и успешно доставлено; это не уникальные посетители и не аудит реальных людей.

| Событие | Что означает |
| --- | --- |
| `page_view` | Страница впервые стала видимой в этой загрузке |
| `wall_view` | Не менее 10% секции Karma Wall попало в видимую область |
| `form_view` | Не менее 10% формы попало в видимую область либо была попытка взаимодействия с формой |
| `form_start` | Первое изменение поля формы |
| `submit_intent` | Первое нажатие отправки, включая невалидную форму |
| `validation_error` | Попытка отправки с невалидными полями или без согласия |
| `security_blocked` | Отправка остановлена без токена либо сервер вернул 403 |
| `security_error` | Ошибка виджета или загрузки Turnstile |
| `rate_limited` | Сработала локальная пауза или сервер вернул 429 |
| `submit_attempt` | Запущен запрос отправки после локальных проверок |
| `submit_success` | Браузер получил `success:true`: сообщение принято **на модерацию** |
| `submit_error` | Ошибка запроса, ответа сервера, сети или таймаут |

Если IntersectionObserver недоступен, события видимости не выдумываются. Взаимодействие с формой всё равно может дать `form_view`/`form_start`.

`analytics/report.sql` выводит суточные значения, дату начала сбора, достигшие лимита типы событий и отношения:

- `form_starts / page_views` — как часто загрузки переходят к заполнению;
- `submit_successes / page_views` — приближённая доля загрузок с принятым сообщением;
- `submit_successes / submit_attempts` — приближённая успешность отправки.

Это отношения агрегатов, а не связанная пользовательская воронка. Отдельные запросы могут потеряться; переход через полночь UTC может разнести этапы по разным датам. Ошибка и успех могут присутствовать для одной страницы. Значения иногда могут превышать 100%; их нельзя молча ограничивать или выдавать за точную долю людей. Публикация после модерации не измеряется — она остаётся отдельным процессом.

## Как различать трафик и затруднения участия

Ниже **условные примеры**, не исторические данные сайта:

| Наблюдение после запуска | Возможное объяснение и проверка |
| --- | --- |
| 20 загрузок за неделю, 2 принятые отправки | Данных мало; сначала проверить исправность приёмника и доставку, затем источники привлечения. Делать вывод об отторжении дизайна рано. |
| 1000 загрузок, 15 просмотров формы | Форму мало замечают/до неё не доходят; проверить путь к участию. |
| 1000 загрузок, 200 начал заполнения, 100 попыток, 5 успехов | Входящий трафик есть; проверить ошибки формы, Turnstile, лимиты и сеть. |
| Есть просмотры формы и начала заполнения, но мало нажатий отправки | Проверить понятность формы и согласия; аналитика указывает этап, но сама не устанавливает причину. |

Сначала анализировать несколько дней/неделю и проверять, что не достигнут лимит. Отсутствие строк отчёта означает отсутствие измерений, а не доказанные нулевые посещения. JS-блокировщики, DNT/GPC, боты и сетевые ошибки искажают охват. Новые счётчики ничего не восстанавливают за прошедшие 15 дней.

## Защита от ошибок и злоупотреблений

Приёмник принимает только POST с разрешённого Origin и JSON до 64 байт с одним полем `event`. Неизвестные события, дополнительные поля и URL с query отвергаются. CORS/Origin ограничивает браузеры, но не доказывает подлинность человека: внешний клиент может подделать Origin. Счётчики ориентировочные, их нельзя использовать для платежей или финансового учёта.

Атомарный лимит по умолчанию — 50 000 для каждого типа события за сутки. Хранилище ограничено примерно 12 × 90 строками. Лимит ограничивает накопление счётчика, а не число вызовов/расходы платформы. Перед запуском проверить квоты и контроль расходов Cloudflare; никакие платные ресурсы этой работой не создавались. IP-лимитов и дополнительных CAPTCHA для аналитики нет.

Запрос аналитики не ожидается формой, имеет таймаут 2,5 секунды и не повторяется. Отказ аналитики не меняет результат отправки, не отключает Turnstile и не создаёт сообщение. Все шесть языков сохранены, пояснение о приватности добавляется к существующей заметке на соответствующем языке только при включённой функции.

## Проверки реализации

- Полный `npm test`: существующие 35 сценариев Edge Function, шесть языков и 84 ключа интерфейса, безопасное отображение сообщений, криптопроверки, сканер и SQL-контракты.
- Новые тесты: выключатели, DNT/GPC, скрытая вкладка, повторные события, события ошибок/успеха, шесть переводов приватности, работа формы при синхронном/асинхронном отказе аналитики, таймаут, whitelist, размер запроса, отсутствие HTTP-пересылки/идентификаторов.
- Реальная локальная SQLite выполняет схему, SQL отчёта, атомарное увеличение с лимитом, границы очистки и запрет включения без даты начала. HTTP-обработчик проходит интеграционный тест через транзакционную имитацию binding D1.
- Проверка конфигурации/сборки Worker: Wrangler 4.156.0, `deploy --dry-run`, без загрузки в Cloudflare. Версия фиксируется в командах, зависимости сайта не добавляются.
- Дополнительный запуск эмулятора `wrangler d1 execute --local` заблокирован автоматической проверкой безопасности: Wrangler неожиданно обратился к `workers.cloudflare.com`, назначение/состав запроса не были установлены. Повторного запуска или обхода блокировки не было. Проверка в эмуляторе не заявляется пройденной; безопасная альтернатива — выполненные локальные SQLite-тесты схемы, SQL и HTTP-обработчика без сети.
- Все локальные данные синтетические. Работа Cloudflare в размещённой среде, фактические журналы и проверка на физическом Samsung ещё не подтверждены: это проверки после разрешения на запуск.

## Порядок запуска после утверждения

Эти шаги **не выполнены** в рамках подготовки PR:

1. Убедиться, что владелец утвердил внедрение; проверить аккаунт Cloudflare, квоты и права Workers/D1. Проверить наличие внешней аналитики в панели аккаунта перед созданием ресурсов.
2. Создать выделенную базу D1 `karma-private-analytics`, заменить нулевой `database_id` реальным. Применить `analytics/schema.sql` только к этой базе. Таблицы по умолчанию не собирают данные.
3. Развернуть Worker с `ANALYTICS_ENABLED="false"` и отключённым журналированием. Не добавлять Tail/Logpush/log destinations. Убедиться в фактической конфигурации панели аккаунта.
4. В изолированной тестовой среде проверить CORS, лимиты, отчёт и отсутствие IP/текстов/идентификаторов в аналитической базе и журналах. Временное логирование посетителей для этой проверки запрещено.
5. Проверить нативные bindings D1 и реальную доставку синтетических событий; тестовые агрегаты удалить до начала реальных измерений. Подтвердить выключенный сбор на действующей странице до финального шага.
6. Задать дату старта и включить настройку D1: `UPDATE analytics_settings SET enabled=1, collection_started_at=coalesce(collection_started_at,datetime('now')) WHERE singleton=1;`. Включить Worker, задать утверждённый HTTPS `/collect` URL и включить клиентский флаг отдельным согласованным изменением.
7. На реальном браузере проверить Network: payload только `event`, нет Cookie/Referer/содержимого формы; DNT/GPC прекращают сбор; форма и Turnstile работают. Выполнить `analytics/report.sql` через авторизованный D1 доступ. Первый день и неделю трактовать с учётом фактического времени запуска.

Для остановки достаточно выключить Worker или D1; клиентский флаг тоже можно выключить. При остановке не очищать старую статистику и не переписывать дату начала. После перерыва нельзя считать отсутствующие даты днями с нулём посетителей. Для очистки агрегатов без трафика использовать `DELETE FROM daily_counts WHERE day < date('now','-89 days');` через авторизованный D1 доступ.
